========================================================================
개폐기 카드 제어 — API/MQTT 연동 스펙 (v2)
WeBee mobile · door-opener
작성일 2026-09-12 · 최종수정 2026-09-13
대상: 백엔드 개발자
========================================================================

이 문서는 온라인 모드(앱 → 서버 → 개폐기)에서 개폐기 카드를 실제로
구동하기 위한 요청/응답 페이로드를 고정합니다. 이 문서에 나온 JSON
구조 그대로 구현하면 됩니다 — 임의로 필드를 더하거나 빼지 말아주세요.

채널:        REST API + MQTT
카드 종류:    8개 (기본 6종 + 커스텀 시간제어 4종 하위분류)
payload 종류:  2개 (TIME / COUNT)
v2 변경사항:  §8 실행 취소, §9 적용 중 명령 조회 추가
             — 기존 §1~7 엔드포인트/토픽/payload는 변경 없음


목차
----
 1. 전체 흐름
 2. 카드 종류 (cardType)
 3. 공통 요청 봉투 (Envelope)

    4-1 파라미터 없음 (OPEN_NOW/CLOSE_NOW/COUNT_STATUS)
    4-2 TIME 그룹 (OPEN_AT/CLOSE_AT/WINDOW/ALTERNATE_24H)
    4-3 COUNT 그룹 (COUNT_CONTROL)
 5. REST API
 6. MQTT
 --- 여기부터 v2 추가사항 ---
 8. 실행 취소 (CANCEL)
 9. 적용 중 명령 조회
 7. 구현 체크리스트
    부록 · enum/포맷 요약


========================================================================
1. 전체 흐름
========================================================================

앱은 항상 REST로 서버에 말하고, 서버는 항상 MQTT로 개폐기에 말합니다.
앱이 개폐기와 직접 통신하는 경로는 없습니다.

    [앱] --POST /commands (REST)--> [백엔드] --MQTT publish--> [개폐기]
    [앱] <--GET status (polling)-- [백엔드] <--MQTT publish-- [개폐기]

    앱:      mobile / door-opener, 사용자가 카드 탭
    백엔드:   REST <-> MQTT broker, 검증 · commandId 발급
    개폐기:   MAC / gateId, 명령 실행 · 결과 응답

토픽/엔드포인트는 카드 종류별로 나누지 않고 각각 1개만 사용합니다.

화면 흐름:
 1) 카드 탭 — 온라인 모드에서 사용자가 "개폐기 카드" 그리드의 흰 카드
    중 하나를 탭합니다.
 2) 개폐기 선택 — "적용할 개폐기 선택" 시트에서 대상 개폐기(1개 이상)를
    고릅니다.
 3) 명령 전송 — 앱이 선택한 개폐기마다 1건씩
    POST /api/v1/gates/{gateId}/commands 를 호출합니다.
 4) MQTT publish — 백엔드는 요청을 검증한 뒤 MQTT로 해당 개폐기에
    명령을 publish하고, API 응답으로 "접수됨"을 반환합니다.
 5) 결과 publish — 개폐기가 명령을 처리한 결과를 MQTT로 백엔드에
    publish합니다.
 6) 결과 확인 — 앱은 GET /commands/{commandId} 를 짧게 폴링해
    성공/실패를 확인합니다 (§6-4).


========================================================================
2. 카드 종류 (cardType)
========================================================================

기본 6종 중 4종은 "시간 제어" 계열로 페이로드 구조가 동일하고, 1종은
"카운트 확인"(파라미터 없음), 1종은 "벌 마릿수 제어"로 완전히 다른
구조입니다. 커스텀 카드 추가 화면은 "시간 제어" 탭 안에서 4개 기능 중
하나를 고르는 구조라, 결국 고유한 payload 모양은 2가지(TIME / COUNT)
뿐입니다.

  cardType         화면 이름                  payload 그룹
  ---------------  -------------------------  -------------
  OPEN_NOW         ON (즉시 열기)               없음
  CLOSE_NOW        OFF (즉시 닫기)              없음
  COUNT_STATUS     COUNT (출입 카운트 확인)      없음
  OPEN_AT          열기 예약                   TIME
  CLOSE_AT         닫기 예약                   TIME
  WINDOW           여닫기 (시간대 운영)          TIME
  ALTERNATE_24H    24시간 교대                 TIME
  COUNT_CONTROL    벌 마릿수 제어               COUNT

▶ 요청 payload는 2종류(TIME / COUNT)만 만들면 됩니다. 엔드포인트/토픽도
  각각 1개로 통일하고 cardType으로 분기하세요. 3개씩 따로 만들 필요
  없습니다.

ON / OFF / COUNT 3개는 항상 존재하는 기본 카드라 커스텀 카드 추가
화면에서는 만들 수 없고 수정도 불가한 고정 카드입니다.


========================================================================
3. 공통 요청 봉투 (Envelope)
========================================================================

모든 카드 종류가 이 구조를 그대로 씁니다. payload 안쪽 모양만
cardType에 따라 달라집니다.

{
  "gateId": "AA:BB:CC:DD:EE:FF",   // 개폐기 MAC 주소, 콜론 포함 대문자 고정
  "cardType": "WINDOW",             // 아래 8개 값 중 하나
  "title": "09:00~14:00 여닫기",     // 앱이 자동 생성, 최대 40자
  "memo": "남쪽 과수원 아침 개방",    // 선택값, 없으면 키 자체 생략
  "payload": { }                    // cardType별로 다름 — 4장 참고
}

필드         타입       필수         설명
-----------  ---------  -----------  ----------------------------------
gateId       string     필수         정규식 ^([0-9A-F]{2}:){5}[0-9A-F]{2}$
cardType     enum       필수         8개 값 고정 (§2 표)
title        string     필수         최대 40자
memo         string     선택         최대 40자. 없으면 키 생략(빈 문자열 X)
payload      object     cardType별   §4 참고


========================================================================
4. cardType별 payload 상세
========================================================================

--------------------------------------------------------------
4-1. 파라미터 없음 — OPEN_NOW / CLOSE_NOW / COUNT_STATUS
--------------------------------------------------------------

{
  "gateId": "AA:BB:CC:DD:EE:FF",
  "cardType": "OPEN_NOW",
  "title": "ON"
}

payload 키 자체를 생략하거나 "payload": {} 둘 다 허용합니다. 백엔드는
무시하면 됩니다. 이 3개 기본 카드에는 메모 입력 UI가 없어 memo도 항상
생략됩니다.


--------------------------------------------------------------
4-2. TIME 그룹 — OPEN_AT / CLOSE_AT / WINDOW / ALTERNATE_24H
--------------------------------------------------------------

{
  "gateId": "AA:BB:CC:DD:EE:FF",
  "cardType": "WINDOW",
  "title": "09:00~14:00 여닫기",
  "memo": "남쪽 과수원 아침 개방",
  "payload": {
    "start": "09:00",       // "HH:MM", cardType에 따라 없을 수 있음
    "end": "14:00",         // "HH:MM", cardType에 따라 없을 수 있음
    "repeat": true          // 매일 반복이면 true
  }
}

  cardType         start                                    end     의미
  ---------------  ---------------------------------------  ------  --------------------------
  OPEN_AT          "09:00"                                  생략     이 시각에 연다
  CLOSE_AT         생략                                      "18:00" 이 시각에 닫는다
  WINDOW           "09:00"                                  "14:00" start~end만 열고 나머지는
                                                                      닫는다. 두 값은 항상 최소
                                                                      1시간 차이(프론트 강제)
  ALTERNATE_24H    "close_first" / "open_first"              생략     24시간 단위로 닫힘→열림
                   (시각 아닌 리터럴 문자열)                            또는 열림→닫힘 교대

▲ 주의: ALTERNATE_24H만 예외 — start가 시각이 아니라 "close_first" /
  "open_first" 리터럴 문자열입니다. 검증 로직에서 cardType별로 타입이
  달라진다는 점을 반영해야 합니다.

예시 · 열기 예약:
{
  "gateId": "AA:BB:CC:DD:EE:FF",
  "cardType": "OPEN_AT",
  "title": "09:00 열기",
  "payload": { "start": "09:00", "repeat": false }
}

예시 · 24시간 교대:
{
  "gateId": "AA:BB:CC:DD:EE:FF",
  "cardType": "ALTERNATE_24H",
  "title": "24시간 교대",
  "memo": "개화 30~60%",
  "payload": { "start": "close_first", "repeat": true }
}


--------------------------------------------------------------
4-3. COUNT 그룹 — COUNT_CONTROL (벌 마릿수 제어)
--------------------------------------------------------------

"현재 활동중인 벌 마릿수"(= 출구로 나간 수 − 입구로 들어온 수, 밖에
나가 있는 벌 수)를 기준으로 low~high 사이 구간과 high 이상 구간, 총
2구간으로 나눠 각 구간마다 입구/출구를 열지 닫을지를 따로 정합니다.
여기에 반복 요일과 감시 시간대를 곱해서 조건이 전부 맞을 때만 규칙이
적용됩니다.

{
  "gateId": "AA:BB:CC:DD:EE:FF",
  "cardType": "COUNT_CONTROL",
  "title": "3~12마리 구간 제어",
  "memo": "남쪽 과수원",
  "payload": {
    "days": ["mon", "wed", "fri"],   // 빈 배열/null = 단발성
    "countRange": { "low": 3, "high": 12 },
    "timeWindow": { "start": "00:00", "end": "24:00" },
    "rules": {
      "within": { "entranceOpen": true,  "exitOpen": true  },
      "above":  { "entranceOpen": true,  "exitOpen": false }
    }
  }
}

필드                      타입              설명
------------------------  ----------------  --------------------------------
days                      string[] | null   요일 코드 배열(sun~sat 중 일부).
                                             빈 배열/null = 단발성.
                                             7개 전부면 "매일"
countRange.low/high       int               0 <= low <= high <= 99
timeWindow.start/end      "HH:MM"           30분 단위. end는 "24:00"까지 허용
rules.within              {entranceOpen,    low~high 구간일 때 개폐
                            exitOpen}
rules.above               {entranceOpen,    high 이상 구간일 때 개폐
                            exitOpen}

▲ 주의: 구간은 2개뿐 — "low마리 미만" 구간은 UI에서 제거되어 존재하지
  않습니다. 반드시 within / above 2개 키만 옵니다(과거 버전의 below
  키는 현재 프론트에 없음).

예시 · 평일 반복:
{
  "gateId": "AA:BB:CC:DD:EE:FF",
  "cardType": "COUNT_CONTROL",
  "title": "3~12마리 구간 제어",
  "payload": {
    "days": ["mon","tue","wed","thu","fri"],
    "countRange": {"low":3,"high":12},
    "timeWindow": {"start":"00:00","end":"24:00"},
    "rules": {
      "within":{"entranceOpen":true,"exitOpen":true},
      "above":{"entranceOpen":true,"exitOpen":false}
    }
  }
}

예시 · 단발성:
{
  "gateId": "AA:BB:CC:DD:EE:FF",
  "cardType": "COUNT_CONTROL",
  "title": "5~20마리 구간 제어",
  "payload": {
    "days": [],
    "countRange": {"low":5,"high":20},
    "timeWindow": {"start":"09:00","end":"14:00"},
    "rules": {
      "within":{"entranceOpen":true,"exitOpen":true},
      "above":{"entranceOpen":false,"exitOpen":true}
    }
  }
}


========================================================================
5. REST API
========================================================================

--------------------------------------------------------------
5-1. 카드 실행(적용) 요청
--------------------------------------------------------------

POST /api/v1/gates/{gateId}/commands
Content-Type: application/json

Body: §3~4의 envelope 그대로 (path의 gateId와 body의 gateId는
동일해야 함 — body는 명시적 검증용으로 유지 추천).

202 Accepted 응답:
{
  "code": "OK",
  "message": "명령이 접수됐어요.",
  "data": {
    "commandId": "cmd_9f2a1c",
    "gateId": "AA:BB:CC:DD:EE:FF",
    "status": "PENDING"
  }
}

에러 예 · 오프라인:
{
  "code": "GATE_OFFLINE",
  "message": "개폐기가 오프라인 상태예요.",
  "data": null
}

commandId는 백엔드가 발급하는 고유 식별자입니다. MQTT 요청/응답
짝짓기와 앱의 결과 폴링에 쓰입니다.

--------------------------------------------------------------
5-2. 카드 등록/수정/삭제 (커스텀 카드 서버 저장)
--------------------------------------------------------------

이 문서는 "명령 실행"이 핵심이라 5-1만 필수입니다. 다만 커스텀 카드를
서버에 저장해두고 여러 기기에서 동일하게 보려면 기존
GateActionRequest 계열 CRUD를 그대로 쓰되, body를 이 문서의
envelope + payload 구조로 교체해야 합니다. 지금 서버 스펙(title,
actionType, actionTime, repeatEnabled)은 COUNT_CONTROL의
countRange / timeWindow / rules를 담을 필드가 없어 확장이 필요합니다
— 이번 스펙 변경의 핵심 요청 사항입니다.


========================================================================
6. MQTT
========================================================================

--------------------------------------------------------------
6-1. 토픽
--------------------------------------------------------------

백엔드 → 개폐기 (명령):   gates/{gateId}/command
개폐기 → 백엔드 (결과):   gates/{gateId}/result

토픽도 카드 종류별로 나누지 않고 1개씩만 사용합니다. 메시지 안의
cardType으로 펌웨어가 분기합니다.

--------------------------------------------------------------
6-2. 명령 메시지 (백엔드 → 개폐기)
--------------------------------------------------------------

MQTT payload는 §4 REST payload와 완전히 동일한 구조를 씁니다 — 새로
설계하지 않고, 앱이 보낸 요청의 cardType/payload를 그대로 옮기고
commandId 한 필드만 얹어 publish합니다. (title/memo는 사람이 보는
UI 텍스트라 개폐기가 알 필요 없어 제외)

공통 뼈대:
{
  "commandId": "cmd_9f2a1c",   // REST 응답(§5-1)에서 발급받은 값 그대로
  "gateId": "AA:BB:CC:DD:EE:FF",
  "cardType": "...",           // §2의 8개 값 중 하나, REST 요청과 동일
  "payload": { ... }           // §4와 완전히 동일한 모양
}

cardType별 MQTT payload (§4와 100% 동일):
  OPEN_NOW       없음 — payload 키 생략 또는 {}
  CLOSE_NOW      없음 — payload 키 생략 또는 {}
  COUNT_STATUS   없음 — payload 키 생략 또는 {}
  OPEN_AT        { "start": "09:00", "repeat": false }
  CLOSE_AT       { "end": "18:00", "repeat": false }
  WINDOW         { "start": "09:00", "end": "14:00", "repeat": true }
  ALTERNATE_24H  { "start": "close_first", "repeat": true }
  COUNT_CONTROL  { "days": [...], "countRange": {...},
                   "timeWindow": {...}, "rules": {...} } — §4-3 예시 그대로

예시 · WINDOW:
{
  "commandId": "cmd_9f2a1c",
  "gateId": "AA:BB:CC:DD:EE:FF",
  "cardType": "WINDOW",
  "payload": { "start": "09:00", "end": "14:00", "repeat": true }
}

예시 · COUNT_CONTROL:
{
  "commandId": "cmd_a1b2c3",
  "gateId": "AA:BB:CC:DD:EE:FF",
  "cardType": "COUNT_CONTROL",
  "payload": {
    "days": ["mon","wed","fri"],
    "countRange": {"low":3,"high":12},
    "timeWindow": {"start":"00:00","end":"24:00"},
    "rules": {
      "within":{"entranceOpen":true,"exitOpen":true},
      "above":{"entranceOpen":true,"exitOpen":false}
    }
  }
}

▶ 백엔드는 cardType/payload를 파싱하거나 변형하지 않고 그대로
  릴레이하면 됩니다. 새 스키마를 따로 설계할 필요가 없습니다 —
  검증도 §3~4의 규칙 한 벌만 있으면 REST 입구와 MQTT 출구 양쪽에
  다 쓸 수 있습니다.

- QoS 1 권장(최소 1회 도달 보장). "최신 명령 1건 실행" 의미이므로
  retain은 사용하지 않습니다.

▲ 펌웨어 파싱 확인 필요 — 이 문서의 payload 모양은 "서버가 앱과
  주고받는 계약"을 고정한 것입니다. 개폐기 펌웨어가 JSON을 이
  필드명 그대로 파싱할 수 있는지(특히 ALTERNATE_24H의
  "close_first"/"open_first" 리터럴, COUNT_CONTROL의 중첩 객체
  구조)는 하드웨어팀과 별도 확인이 필요합니다. 펌웨어가 이 모양을
  그대로 받을 수 없다면, 백엔드가 이 JSON을 펌웨어 전용의 더 가벼운
  포맷으로 변환하는 어댑터 한 겹을 추가하되 REST 쪽 계약(§3~4)은
  그대로 유지해주세요 — 앱은 이 문서만 보고 만들었습니다.

--------------------------------------------------------------
6-3. 결과 메시지 (개폐기 → 백엔드)
--------------------------------------------------------------

{
  "commandId": "cmd_9f2a1c",
  "gateId": "AA:BB:CC:DD:EE:FF",
  "status": "OK",          // "OK" | "ERROR"
  "detail": null           // ERROR일 때 사유 문자열
}

백엔드는 이 메시지를 받으면 commandId로 5-1에서 발급한 명령 레코드를
찾아 상태를 SUCCESS/FAILED로 갱신합니다.

--------------------------------------------------------------
6-4. 앱이 결과를 받는 방법
--------------------------------------------------------------

HTTP · 폴링 (추천):
GET /api/v1/gates/{gateId}/commands/{commandId}

{
  "code": "OK", "message": "OK",
  "data": { "commandId": "cmd_9f2a1c", "status": "SUCCESS", "detail": null }
}

status: PENDING → SUCCESS | FAILED | TIMEOUT
(예: 15초 안에 개폐기 응답이 없으면 백엔드가 자체적으로 TIMEOUT
처리). 앱은 1~2초 간격으로 최대 15~20초까지 폴링합니다.

SSE/웹소켓 확장은 추후 옵션입니다(이미 hive 텔레메트리용 SSE가 있어
나중에 gate-command-result 이벤트로 확장 가능) — 초기 구현은
폴링으로 충분합니다.


========================================================================
여기부터 v2 추가사항
========================================================================

§1~7(엔드포인트, 토픽, cardType/payload 구조)은 v1과 완전히 동일하며
변경 없습니다. §8~9는 "① 실행 중인 명령을 취소하는 기능"과 "② 개폐기에
지금 어떤 명령이 적용돼 있는지 조회하는 기능"을 기존 REST/MQTT 위에
필드 추가로만 얹습니다. 새 엔드포인트나 새 토픽은 만들지 않습니다.


========================================================================
8. 실행 취소 (CANCEL)
========================================================================

기존 실행 API(POST /api/v1/gates/{gateId}/commands)와 MQTT 명령
토픽(gates/{gateId}/command)을 그대로 쓰되, operation 필드로 "실행"과
"취소"를 구분합니다. 새 주소는 없습니다.

--------------------------------------------------------------
8-1. 실행 요청 — operation 필드만 추가
--------------------------------------------------------------

기존 §3~4의 envelope과 payload는 그대로입니다. operation: "EXECUTE"
한 필드만 추가됩니다(생략 시 기본값도 EXECUTE로 처리해, v1으로 만든
클라이언트가 있어도 깨지지 않게 해주세요).

실행 요청 예 (WINDOW):
{
  "gateId": "AA:BB:CC:DD:EE:FF",
  "operation": "EXECUTE",          // 신규. 생략 시 기본값 EXECUTE
  "cardType": "WINDOW",
  "title": "09:00~14:00 여닫기",
  "memo": "남쪽 과수원 아침 개방",
  "payload": { "start": "09:00", "end": "14:00", "repeat": true }
}

--------------------------------------------------------------
8-2. 취소 요청
--------------------------------------------------------------

취소할 대상은 targetCommandId(취소하려는 실행이 §5-1 응답으로
받았던 commandId)로 특정합니다. cardType/title/payload는 필요
없습니다 — 이미 서버가 그 commandId로 무엇이 실행 중인지 알고 있기
때문입니다.

취소 요청:
{
  "gateId": "AA:BB:CC:DD:EE:FF",
  "operation": "CANCEL",
  "targetCommandId": "cmd_original"
}

- 취소 요청도 §5-1과 동일하게 새 commandId를 발급받습니다. 이
  commandId와 취소 대상인 targetCommandId는 서로 다른 값이니
  응답·로그에서 구분해 표기해주세요.
- 서버는 MQTT 명령 메시지에 operation: "CANCEL"과 targetCommandId를
  그대로 실어 개폐기에 전달합니다. 취소가 실제로 어떻게
  처리되는지(문을 어떻게 둘지 등)는 개폐기가 알아서 처리하며,
  서버는 이 두 필드를 그대로 전달하기만 하면 됩니다.

--------------------------------------------------------------
8-3. 결과 MQTT 확장 — 취소 결과 보고
--------------------------------------------------------------

기존 결과 토픽(gates/{gateId}/result)을 그대로 쓰고, 기존
status: "OK" | "ERROR"(명령 처리 성공/실패)는 의미가 바뀌지
않습니다. 여기에 취소 대상을 가리키는 executionCommandId와, 그
실행이 지금 켜져 있는지를 나타내는 executionStatus 2개 필드만
추가합니다.

필드                 값           의미
-------------------  -----------  ----------------------------------
executionCommandId   string       상태가 바뀐 원래 실행의 commandId
                                   (§5-1에서 발급된 값)
executionStatus      ACTIVE       규칙이 개폐기에 적용되어 유지 중
                      CANCELLED   사용자가 §8-2로 취소함

예시 · 취소 성공:
{
  "commandId": "cmd_cancel",
  "gateId": "AA:BB:CC:DD:EE:FF",
  "status": "OK",
  "detail": null,
  "executionCommandId": "cmd_original",
  "executionStatus": "CANCELLED"
}

- 실행 요청이 성공하면 그 결과 메시지에 executionCommandId(자기
  자신의 commandId)와 executionStatus: "ACTIVE"를 함께 보고합니다.
- 취소 요청이 성공하면 취소 요청 자신의 commandId와 함께,
  executionCommandId에 취소 대상(targetCommandId와 같은 값)을,
  executionStatus: "CANCELLED"를 보고합니다.
- 실행/취소가 실패(status: "ERROR")했을 때는 executionStatus를
  바꾸지 않습니다 — 성공한 것처럼 상태를 보내지 않습니다.


========================================================================
9. 적용 중 명령 조회
========================================================================

"지금 이 개폐기에 어떤 카드가 적용돼 있는지"를 온라인 모드에서
확인하기 위한 조회 전용 API입니다. 온라인 모드에서 실행한 명령
(§5-1)에 한정되며, NFC 태깅으로 로컬에서 적용한 카드는 이 API의
대상이 아닙니다(그 경우는 휴대폰에만 상태가 남습니다).

GET /api/v1/gates/{gateId}/commands/current

200 · 적용 중인 명령 있음:
{
  "code": "OK", "message": "OK",
  "data": {
    "commandId": "cmd_original",
    "cardType": "WINDOW",
    "title": "09:00~14:00 여닫기",
    "memo": "남쪽 과수원 아침 개방",
    "payload": { "start": "09:00", "end": "14:00", "repeat": true },
    "executionStatus": "ACTIVE",
    "appliedAt": "2026-09-13T09:00:00+09:00"
  }
}

200 · 적용 중인 명령 없음:
{
  "code": "OK", "message": "OK",
  "data": null
}

- data는 executionStatus: "ACTIVE"인 실행이 있을 때만 채워지고,
  없으면 null입니다(404가 아니라 200 + null — "조회 자체는 정상,
  다만 적용된 게 없음"을 표현).
- 응답의 cardType/payload 모양은 §4와 동일합니다.
- 이 API는 §8-3의 MQTT 상태 메시지를 서버가 누적 반영한 결과를
  읽는 것으로, 별도의 실시간 조회를 개폐기에 다시 요청하지
  않습니다(앱이 화면을 열 때마다 폴링해도 개폐기 트래픽이 늘지
  않도록).


========================================================================
7. 구현 체크리스트
========================================================================

 1. REST  POST /api/v1/gates/{gateId}/commands — envelope 그대로
    받아 검증 후 MQTT publish, commandId 발급 (§5-1)
 2. REST  GET /api/v1/gates/{gateId}/commands/{commandId} — 상태
    조회 (§6-4)
 3. MQTT  gates/{gateId}/command publish (§4 payload를 그대로
    릴레이 + commandId), gates/{gateId}/result subscribe (§6-1~3)
 4. Validation  cardType별로 §3~4 표의 필드 유무·타입을 그대로
    검증 — 특히 ALTERNATE_24H.start가 시각이 아닌 리터럴인 점,
    COUNT_CONTROL은 within/above 2구간뿐인 점
 5. 선택  기존 커스텀 카드 CRUD 스펙도 이 envelope 구조로 교체
    (§5-2)
 6. v2 · REST/MQTT  실행 요청에 operation 필드 추가(기본값
    EXECUTE), 취소 요청(operation: "CANCEL" + targetCommandId)
    처리 — 기존 주소 그대로 (§8-1~2)
 7. v2 · MQTT 결과  executionCommandId/executionStatus 필드 추가
    — 실행 성공 시 ACTIVE, 취소 성공 시 CANCELLED (§8-3)
 8. v2 · REST 신규  GET /api/v1/gates/{gateId}/commands/current —
    적용 중 명령 조회 (§9)
